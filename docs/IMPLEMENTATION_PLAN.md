> Статус: v0.4 (2026-10-25). Все решения по уточняющим вопросам зафиксированы в разделе 2.
> Max исключён из проекта — уведомления только в Telegram (и позже в веб).
> Документ живой — обновляем по мере работы.

## 1. Что делает сервис

Личный сервис, который **первым** сообщает о новых IT-вакансиях на hh.ru.

Пользователь задаёт фильтры (направление, ключевые слова, город, опыт, зарплата, формат работы, исключения).
Сервис каждую минуту проверяет hh.ru и в течение **1–3 минут** после публикации подходящей вакансии
присылает уведомление **в Telegram**. Позже уведомления появятся и в веб-интерфейсе.
Дальше сервис следит за уже найденными вакансиями и сообщает, если вакансию закрыли, перенесли в архив
или в ней поменялась зарплата или другие важные поля.

### Интерфейсы

В каждом интерфейсе можно смотреть и менять фильтры:

| Интерфейс | Назначение |
|---|---|
| **Telegram-бот** | Уведомления + управление подписками |
| **Веб-интерфейс** | Удобный конструктор фильтров, лента вакансий, история изменений |

### Ключевые сценарии

1. Вход: в боте — по `/start`, на сайте — по email (одноразовый код на почту).
2. Создание подписки (набор фильтров). Подписок может быть несколько: «Frontend», «Backend», «Техподдержка».
3. Сразу после создания подписки приходят вакансии **за последние 24 часа**.
4. Дальше приходят новые вакансии, как только они появляются.
5. Уведомления об изменениях: закрыта / в архиве / изменилась зарплата / изменились условия.
6. Подписку можно поставить на паузу, изменить или удалить из любого интерфейса.

## 3. Источник данных: hh.ru

### 3.1. Официальный API (основной источник, бесплатно)

API бесплатен и не требует прокси, поэтому это основной источник. Парсинг его дополняет.

```
GET https://api.hh.ru/vacancies          — поиск
GET https://api.hh.ru/vacancies/{id}     — детали вакансии (в т.ч. признак archived)
GET https://api.hh.ru/professional_roles — справочник проф. ролей (нужен для пресетов)
GET https://api.hh.ru/areas              — регионы
GET https://api.hh.ru/dictionaries       — опыт, занятость, график, валюты
```

Параметры поиска:

| Параметр | Назначение |
|---|---|
| `text` | Поисковая строка, поддерживает язык запросов: `NAME:(frontend OR react) NOT senior` |
| `professional_role` | Проф. роли (можно несколько): программист/разработчик, специалист техподдержки и т.д. |
| `area` | Регион |
| `experience` | `noExperience`, `between1And3`, … |
| `schedule` / `employment` | Удалёнка, гибрид, полный день и т.д. |
| `salary`, `currency`, `only_with_salary` | Зарплата |
| `date_from` | Вакансии, опубликованные позже указанного момента (по нему ищем новые) |
| `order_by=publication_time` | Сначала свежие |
| `per_page=100`, `page` | Пагинация |

Важно:

- Обязательный заголовок: `HH-User-Agent: getFirstOffer/0.1 (<твой email>)`.
- Приложение регистрируем на https://dev.hh.ru (бесплатно).
- Опрос раз в минуту по нескольким подпискам — это несколько запросов в минуту, вполне безопасная нагрузка.
- `date_from` берём с запасом в 5 минут, а дубли отсекаем в БД: вакансия может попасть в поисковый индекс hh позже, чем указано в её `published_at`.

### 3.2. Парсинг сайта (дополнительный источник)

Зачем он нужен:
1. **Скорость.** Есть гипотеза, что вакансия может появиться в поиске на сайте раньше, чем в API. Проверим её замером на этапе 3: если гипотеза не подтвердится, парсер для поиска можно не включать.
2. Данные или фильтры, которых нет в API.

Как парсим без прокси и бюджета:
- Парсим страницу поиска `hh.ru/search/vacancy` с сортировкой по дате и параметрами, совпадающими с фильтрами подписки.
- Запрос не чаще одного раза в 1–2 минуты на подписку, со случайной задержкой и нормальным User-Agent.
- Если получили капчу или `403`, автоматически приостанавливаем парсер (backoff на 15–60 минут) и дальше работаем только через API.
- IP-адреса облаков hh.ru блокирует чаще, чем домашние. Если с VM в Yandex Cloud будут постоянные блокировки, запасной план — запускать парсер на домашнем компьютере или Raspberry Pi: он будет писать в ту же БД или отправлять данные в API.
- Риск: парсинг противоречит пользовательскому соглашению hh.ru. Для личного использования с низкой частотой запросов риск минимальный, но парсер держим за флагом `PARSER_ENABLED`.

Оба источника реализуют общий интерфейс `VacancySource`, поэтому дальнейшая обработка не зависит от того, откуда пришла вакансия.

## 4. Архитектура

```
 ┌───────────────┐            ┌───────────────┐
 │ Telegram-бот  │            │   Web (SPA)   │
 └───────┬───────┘            └───────┬───────┘
         │ команды                    │ REST
         └──────────┬─────────────────┘
                    ▼
          ┌───────────────────┐
          │ Сервисный слой    │  подписки, фильтры, пользователи
          │ + REST API        │  (FastAPI)
          └─────────┬─────────┘
                    │
              ┌─────▼─────┐        ┌─────────────────────┐
              │PostgreSQL │◄───────┤ Fetcher (раз в 60с) │◄── api.hh.ru
              └─────▲─────┘        │ + Parser (опц.)     │◄── hh.ru (HTML)
                    │              └─────────┬───────────┘
                    │              ┌─────────▼───────────┐
                    ├──────────────┤ Tracker (раз в 30м) │◄── api.hh.ru/vacancies/{id}
                    │              └─────────┬───────────┘
                    │                        │ события
                    │              ┌─────────▼───────────┐
                    └──────────────┤ Notifier            ├──► Telegram
                                   │ (по каналам)        ├──► Web Push (позже)
                                   └─────────────────────┘
                     Redis — очередь задач, блокировки, лимиты
```

### Компоненты

| Компонент | Ответственность |
|---|---|
| **Сервисный слой** | Вся бизнес-логика подписок и фильтров. Её используют и бот, и REST API |
| **REST API** | Эндпоинты для веба, вход по email |
| **Telegram-бот** | Диалоги управления подписками. Сами уведомления отправляет Notifier |
| **Fetcher** | Раз в 60 с опрашивает источники по активным подпискам, сохраняет вакансии, создаёт события `new` |
| **Tracker** | Перепроверяет уже найденные вакансии, создаёт события `closed` / `archived` / `salary_changed` / `changed` |
| **Notifier** | Из каждого события делает задачи отправки во все активные каналы пользователя (сейчас — Telegram), с ретраями и учётом статуса доставки |

### Поиск новых вакансий

1. По каждой активной подписке делаем запрос с `date_from = last_checked_at − 5 мин`.
2. Применяем локальные фильтры, которых нет в API: стоп-слова и чёрный список работодателей.
3. Пытаемся сохранить пару `(subscription_id, vacancy_id)` в `subscription_matches`. Если вставка прошла, вакансия новая, и создаём событие `new`. Если сработал конфликт, пропускаем.
4. Когда одна вакансия подходит под несколько подписок, пользователь получает **одно** уведомление, где перечислены названия подписок. Дедупликация идёт по `(user_id, vacancy_id)`.

Подгрузка за 24 часа: при создании подписки и при изменении её фильтров запускается разовая задача с `date_from = now − 24h`. Такие уведомления помечаются «📦 за последние 24 ч», чтобы их было легко отличить от свежих.

### Отслеживание изменений

- Отслеживаем вакансии, у которых есть совпадения и которые не закрыты, за последние **30 дней** (срок настраивается).
- Раз в 30 минут делаем `GET /vacancies/{id}`. Запросы распределяем по времени, чтобы не отправлять их пачкой.
- Сравниваем с последним снимком такие поля: `archived`, зарплату (`from`/`to`/`currency`/`gross`), график, занятость, опыт, название, адрес. Если вакансия возвращает `404`, считаем её удалённой.
- При изменении сохраняем новый снимок, создаём событие и отправляем уведомление вида
  «💰 Зарплата изменилась: 120–150k → 150–180k» или «🗄 Вакансия перенесена в архив».

## 6. Модель данных

```
users
  id                PK
  email             text UNIQUE NULL
  created_at

user_channels                       -- каналы уведомлений и управления
  id                PK
  user_id           FK → users
  type              enum('telegram', 'web')
  external_id       text            -- chat_id в Telegram
  is_active         bool            -- false, если бот заблокирован
  UNIQUE(type, external_id)

email_login_codes
  email, code_hash, expires_at, used_at

subscriptions
  id                PK
  user_id           FK → users
  name              text            -- «Frontend», «Backend», «Техподдержка»
  filters           jsonb           -- параметры запроса к hh.ru (text, professional_role, area, ...)
  exclude_words     text[]          -- стоп-слова
  exclude_employers text[]          -- id работодателей hh.ru
  is_active         bool
  last_checked_at   timestamptz
  created_at, updated_at

vacancies
  id                text PK         -- id вакансии на hh.ru
  name              text
  employer_id       text
  employer_name     text
  area              text
  salary_from       int NULL
  salary_to         int NULL
  salary_currency   text NULL
  salary_gross      bool NULL
  url               text
  status            enum('open', 'archived', 'closed')
  published_at      timestamptz
  first_seen_at     timestamptz     -- когда мы её нашли (для замера скорости)
  first_seen_source enum('api', 'parser')
  last_checked_at   timestamptz
  raw               jsonb

vacancy_snapshots                   -- история для отслеживания изменений
  id                PK
  vacancy_id        FK → vacancies
  data              jsonb           -- отслеживаемые поля
  taken_at          timestamptz

subscription_matches
  subscription_id   FK → subscriptions
  vacancy_id        FK → vacancies
  is_backfill       bool            -- найдена при подгрузке за 24 ч
  matched_at        timestamptz
  PRIMARY KEY (subscription_id, vacancy_id)

vacancy_events                      -- что сообщаем пользователю
  id                PK
  user_id           FK → users
  vacancy_id        FK → vacancies
  type              enum('new', 'archived', 'closed', 'salary_changed', 'changed')
  payload           jsonb           -- что было → что стало
  created_at
  UNIQUE(user_id, vacancy_id, type) WHERE type = 'new'

deliveries                          -- статус отправки по каждому каналу
  event_id          FK → vacancy_events
  channel_id        FK → user_channels
  status            enum('pending', 'sent', 'failed')
  attempts          int
  sent_at           timestamptz NULL
  error             text NULL
  PRIMARY KEY (event_id, channel_id)
```

Разница `first_seen_at − published_at` показывает реальную скорость сервиса. По ней сравниваем API и парсер.

## 7. Пресеты фильтров

Стартовые подписки, все поля потом можно менять:

| Пресет | Основа запроса |
|---|---|
| **Frontend** | роль «Программист, разработчик» + `NAME:(frontend OR фронтенд OR react OR vue OR angular OR javascript OR typescript)` |
| **Backend** | роль «Программист, разработчик» + `NAME:(backend OR бэкенд OR python OR java OR go OR node OR php)` |
| **Техподдержка** | роль «Специалист технической поддержки» (+ при желании `NAME:(поддержка OR support OR helpdesk)`) |
| **IT в целом** | набор IT-ролей из справочника `/professional_roles` (категория «Информационные технологии») |

Общие настройки по умолчанию для всех пресетов (их можно менять в каждой подписке):

| Настройка | Значение | Параметр API |
|---|---|---|
| Регион | Вся Россия | `area=113` |
| Формат | Только удалёнка | `work_format=REMOTE`; если параметр не поддерживается — `schedule=remote` (проверить на этапе 1) |
| Опыт | Без опыта, 1–3 года | `experience=noExperience`, `experience=between1And3` |
| Зарплата | Не ограничена | можно задать `salary` + `only_with_salary` |
| Стоп-слова | `senior`, `lead`, `ведущий`, `руководитель`, `1С` | фильтруем локально |

Точные id ролей берём из `/professional_roles` на этапе 1 и сохраняем в коде как константы.

## 10. Риски

| Риск | Что делаем |
|---|---|
| hh.ru блокирует парсер (особенно с облачного IP) | Backoff и автоотключение; API как основной источник; парсер можно запускать с домашней машины |
| Вакансия попадает в API с задержкой | Запас по `date_from`, замер задержки, парсер как ускоритель |
| Изменение API или вёрстки hh.ru | Изоляция в `sources/`, тесты, алерт, если источник вернул 0 результатов N раз подряд |
| Упал один из мессенджеров | Независимые доставки по каналам с ретраями |
| Слишком много уведомлений | Стоп-слова, чёрный список, кнопка «скрыть компанию» |
| Упал воркер и уведомления не приходят | Healthcheck и алерт в Telegram |
| Расходы в Yandex Cloud | Одна небольшая VM с долей vCPU 20–50%, PostgreSQL в контейнере, бэкапы в Object Storage. Прерываемую VM не берём: её останавливают минимум раз в сутки, и уведомления пропадут |
