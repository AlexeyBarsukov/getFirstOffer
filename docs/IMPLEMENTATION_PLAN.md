## 1. Что делает сервис

Пользователь задаёт фильтры вакансий (профессия, город, зарплата, опыт, формат работы и т.д.).
Сервис регулярно проверяет hh.ru и **как только появляется новая подходящая вакансия — присылает уведомление** в:

- Telegram-бот (MVP);
- мессенджер Max (max.ru) — после MVP;
- собственный веб-интерфейс — после MVP.

### Ключевые сценарии

1. Пользователь запускает бота → регистрируется.
2. Создаёт подписку (набор фильтров). Может иметь несколько подписок.
3. Получает уведомления о новых вакансиях по каждой подписке.
4. Может поставить подписку на паузу, изменить или удалить её.

## 2. Источник данных: hh.ru

### 2.1. Официальный API (основной путь)

В README указана ссылка на **поиск резюме** — это не то, что нам нужно (он для работодателей и требует платного доступа).
Нам нужен **поиск вакансий**:

```
GET https://api.hh.ru/vacancies
```

Полезные параметры:

| Параметр | Назначение |
|---|---|
| `text` | Поисковая строка (поддерживает язык запросов hh: `NAME:python AND junior`) |
| `area` | Регион (справочник `GET /areas`) |
| `professional_role` | Проф. роль (справочник `GET /professional_roles`) |
| `experience` | Опыт: `noExperience`, `between1And3`, … (`GET /dictionaries`) |
| `employment`, `schedule` | Тип занятости и график (в т.ч. удалёнка) |
| `salary`, `currency`, `only_with_salary` | Зарплата |
| `date_from` | Вакансии, опубликованные после указанного момента — **ключевой параметр для поиска «новых»** |
| `order_by=publication_time` | Сортировка по дате публикации |
| `per_page`, `page` | Пагинация (`per_page` до 100, глубина выдачи ограничена ~2000 результатами) |

Важно:

- Обязателен заголовок `HH-User-Agent: getFirstOffer/0.1 (email@example.com)`, иначе запросы могут блокироваться.
- Рекомендуется зарегистрировать приложение на https://dev.hh.ru — получим токен приложения и более стабильные лимиты.
- Есть rate limit (точные значения не публикуются) — нужен троттлинг и обработка `429`/капчи.
- Детали вакансии: `GET /vacancies/{id}`.

### 2.2. Парсинг страниц (запасной путь)

Используем **только** если в API нет нужного фильтра/данных.
Риски: нарушение пользовательского соглашения hh.ru, капча, блокировки по IP, поломка при смене вёрстки.
Поэтому парсер — отдельный модуль за общим интерфейсом `VacancySource`, чтобы его можно было включать/выключать, не трогая остальную систему.

## 3. Архитектура

```
                 ┌──────────────┐
  Telegram  ◄────┤  Bot service │◄──────┐
                 └──────┬───────┘       │
                        │ команды       │ уведомления
                        ▼               │
┌───────────┐    ┌──────────────┐    ┌──┴──────────────┐
│  Web UI   ├───►│   REST API   │    │ Notifier worker │──► Max (позже)
│ (позже)   │    │  (FastAPI)   │    └──▲──────────────┘
└───────────┘    └──────┬───────┘       │ очередь
                        │               │
                 ┌──────▼───────┐    ┌──┴──────────────┐
                 │  PostgreSQL  │◄───┤ Fetcher worker  │──► api.hh.ru
                 └──────────────┘    │  (по расписанию)│
                                     └─────────────────┘
                        Redis — очередь задач, кэш, rate limit
```

### Компоненты

| Компонент | Ответственность |
|---|---|
| **REST API** | CRUD пользователей и подписок, авторизация, отдача данных для веб-интерфейса |
| **Bot service** | Telegram-бот: диалог создания подписок, команды `/start`, `/subscribe`, `/list`, `/pause`, `/delete` |
| **Fetcher worker** | По расписанию опрашивает hh.ru по всем активным подпискам, сохраняет вакансии, определяет новые |
| **Notifier worker** | Берёт новые совпадения из очереди и рассылает по каналам (Telegram, Max, Web) |
| **PostgreSQL** | Основное хранилище |
| **Redis** | Брокер очереди, дедупликация, лимиты запросов |

### Как определяем «новую» вакансию

1. Для каждой подписки храним `last_checked_at`.
2. Запрос к API с `date_from = last_checked_at - небольшой запас (напр. 5 мин)`.
3. Каждую вакансию пытаемся вставить в таблицу `subscription_matches` с уникальным ключом `(subscription_id, vacancy_id)`.
4. Если вставка прошла — это новая вакансия → ставим задачу на уведомление. Если конфликт — уже отправляли, пропускаем.

**Оптимизация:** подписки с одинаковыми фильтрами группируем по хэшу фильтра — один запрос к hh.ru на группу, а не на каждого пользователя.

## 4. Технологический стек (предложение)

| Слой | Инструмент | Почему |
|---|---|---|
| Язык | Python 3.12+ | Быстрый старт, лучшие библиотеки для ботов и парсинга |
| API | FastAPI + Pydantic v2 | Async, автодокументация OpenAPI |
| Telegram | aiogram 3 | Async, FSM для пошаговых диалогов |
| Max | Bot API платформы Max (dev.max.ru) | Официальный API, подключаем позже |
| HTTP-клиент | httpx | Async, ретраи, таймауты |
| БД | PostgreSQL 16 + SQLAlchemy 2 (async) + Alembic | Надёжно, миграции |
| Очередь / планировщик | Redis + arq (или Celery + Beat) | Фоновые задачи и периодический опрос |
| Парсинг (запасной) | selectolax / BeautifulSoup, при необходимости Playwright | |
| Фронтенд (позже) | React/Next.js или Vue | Решим на этапе веб-интерфейса |
| Инфраструктура | Docker + docker-compose, GitHub Actions | Одинаковое окружение локально и на сервере |
| Качество | ruff, mypy, pytest, pre-commit | |
| Наблюдаемость | структурированные логи (structlog), Sentry | |

## 5. Модель данных (MVP)

```
users
  id              PK
  created_at

user_channels                  -- куда слать уведомления
  id              PK
  user_id         FK → users
  type            enum('telegram', 'max', 'web')
  external_id     -- chat_id в Telegram / id в Max
  is_active       bool
  UNIQUE(type, external_id)

subscriptions
  id              PK
  user_id         FK → users
  name            text
  filters         jsonb        -- параметры запроса к hh.ru
  filters_hash    text         -- для группировки одинаковых запросов
  is_active       bool
  last_checked_at timestamptz
  created_at

vacancies
  id              text PK      -- id вакансии на hh.ru
  name            text
  employer_name   text
  area            text
  salary_from     int null
  salary_to       int null
  salary_currency text null
  url             text
  published_at    timestamptz
  raw             jsonb        -- полный ответ API
  fetched_at      timestamptz

subscription_matches
  subscription_id FK → subscriptions
  vacancy_id      FK → vacancies
  notified_at     timestamptz null
  PRIMARY KEY (subscription_id, vacancy_id)
```

## 6. Пошаговый план реализации

### Этап 0. Подготовка (0.5–1 день)
- [ ] Ответить на уточняющие вопросы (раздел 8), зафиксировать решения в этом документе.
- [ ] Зарегистрировать Telegram-бота через @BotFather, получить токен.
- [ ] Зарегистрировать приложение на dev.hh.ru.
- [ ] Настроить репозиторий: структура проекта, `.gitignore` (в т.ч. `.idea/`), `pyproject.toml`, ruff, mypy, pre-commit.
- [ ] `docker-compose.yml`: PostgreSQL + Redis.
- [ ] `.env.example` с переменными: `TELEGRAM_BOT_TOKEN`, `DATABASE_URL`, `REDIS_URL`, `HH_USER_AGENT`.

**Результат:** проект запускается локально одной командой `docker compose up`.

### Этап 1. Клиент hh.ru (1–2 дня)
- [ ] Модуль `hh_client`: поиск вакансий, получение вакансии по id, справочники (`/areas`, `/dictionaries`, `/professional_roles`).
- [ ] Pydantic-модели ответов.
- [ ] Ретраи с экспоненциальной задержкой, обработка `429`, таймауты, ограничение частоты запросов.
- [ ] Интерфейс `VacancySource`, чтобы позже подключить парсер.
- [ ] Тесты на записанных ответах API (без реальных запросов).

**Результат:** можно из кода получить список вакансий по фильтрам.

### Этап 2. База данных (1 день)
- [ ] SQLAlchemy-модели по разделу 5.
- [ ] Alembic: первая миграция.
- [ ] Репозитории (слой доступа к данным) для пользователей, подписок, вакансий, совпадений.

**Результат:** схема БД создаётся миграцией.

### Этап 3. Fetcher — поиск новых вакансий (1–2 дня)
- [ ] Периодическая задача (например, раз в 5 минут) по всем активным подпискам.
- [ ] Группировка подписок по `filters_hash`.
- [ ] Запрос с `date_from`, сохранение вакансий (upsert), запись в `subscription_matches`.
- [ ] Новые совпадения → задача в очередь на уведомление.
- [ ] Защита от первого «залпа»: при создании подписки не слать сотни старых вакансий (см. вопрос 4).

**Результат:** в БД появляются новые совпадения без участия пользователя.

### Этап 4. Telegram-бот (2–3 дня)
- [ ] `/start` — регистрация пользователя и канала Telegram.
- [ ] `/subscribe` — пошаговый диалог (FSM): ключевые слова → город → опыт → зарплата → формат работы → подтверждение.
- [ ] `/list` — список подписок с кнопками «Пауза / Удалить».
- [ ] `/help`.
- [ ] Обработка блокировки бота пользователем (деактивировать канал).

**Результат:** пользователь может управлять подписками в Telegram.

### Этап 5. Notifier — отправка уведомлений (1 день)
- [ ] Воркер читает очередь и отправляет сообщение: название, компания, зарплата, город, кнопка «Открыть на hh.ru».
- [ ] Соблюдение лимитов Telegram (~30 сообщений/сек суммарно, ~1/сек в один чат).
- [ ] Если вакансий много — группировать в одно сообщение-дайджест.
- [ ] Отметка `notified_at`, ретраи при ошибках.

**Результат:** 🎯 **MVP готов** — пользователь получает уведомления в Telegram.

### Этап 6. Деплой MVP (1 день)
- [ ] VPS + docker-compose (или аналог).
- [ ] CI в GitHub Actions: линтеры + тесты.
- [ ] Бэкапы PostgreSQL, логи, Sentry.
- [ ] Healthcheck и алерт, если fetcher перестал работать.

### Этап 7. REST API (2–3 дня)
- [ ] Эндпоинты: `/auth`, `/me`, `/subscriptions` (CRUD), `/subscriptions/{id}/matches`, `/dictionaries`.
- [ ] Авторизация: вход через Telegram Login Widget (или email + magic link) → JWT.
- [ ] Бот переводим на работу через общий сервисный слой, чтобы логика не дублировалась.

### Этап 8. Веб-интерфейс (1–2 недели)
- [ ] Вход, список подписок, удобный конструктор фильтров (автодополнение городов и ролей из справочников).
- [ ] Лента найденных вакансий по каждой подписке.
- [ ] Настройки каналов уведомлений.
- [ ] Уточнить: что значит «2 фронтенда» (см. вопрос 1).

### Этап 9. Уведомления в Max (2–3 дня)
- [ ] Бот на платформе Max, привязка аккаунта Max к пользователю.
- [ ] Адаптер `MaxNotifier` с тем же интерфейсом, что и `TelegramNotifier`.

### Этап 10. Парсер hh.ru (по необходимости)
- [ ] Только для данных, которых нет в API.
- [ ] Реализация `VacancySource` через парсинг, флаг включения в конфиге.

### Этап 11. Развитие (идеи)
- Тихие часы и частота уведомлений (сразу / дайджест раз в день).
- Исключающие слова и чёрный список компаний.
- Отметки «интересно / откликнулся / не интересно».
- Другие источники вакансий (Habr Career, SuperJob, LinkedIn) через тот же `VacancySource`.
- Монетизация (если нужна).

## 8. Уточняющие вопросы

**Продукт**
1. «2 фронтенда» — это веб-сайт + мобильное приложение? Или пользовательский сайт + админка?
2. Сервис для себя/узкого круга или публичный? От этого зависят нагрузка, авторизация, юридические вопросы.
3. Насколько быстро нужно уведомлять: в течение 1–5 минут или достаточно раз в 15–30 минут? Частый опрос = больше запросов к hh.ru.
4. При создании подписки слать уже существующие вакансии (например, за последние 24 часа) или только появившиеся после подписки?
5. Какие фильтры нужны в MVP? Достаточно ли: ключевые слова, город, опыт, зарплата, удалёнка?
6. Нужны ли исключающие слова («не 1С», «не senior») и чёрный список компаний?
7. Одна вакансия под несколько подписок одного пользователя — одно уведомление или несколько?
8. Отслеживать ли изменения уже найденных вакансий (подняли зарплату, закрыли вакансию)?

**Технические**
9. Есть ли предпочтения по языку бэкенда (Python / Go / Java / Node.js)? В документе предложен Python.
10. Где будем хостить: свой VPS, облако (Yandex Cloud, Selectel), бесплатные тарифы?
11. Есть ли бюджет на прокси, если понадобится парсинг?
12. Как пользователь будет входить на сайт: через Telegram, email, телефон?
